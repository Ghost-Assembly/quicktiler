QuickTiler

Keyboard-driven zone tiling for GNOME Shell, with a quick settings tile that lists every shortcut.

Press a direction repeatedly and the focused window cycles through the zones on that side. There is no overlay, no grid picker and no panel button — between keypresses the extension creates no actors, runs no timers and connects to no global signals, so it costs nothing at all.

Zones

Both common ultrawide layouts — 1/4 + 1/2 + 1/4 and 1/2 + 1/2 — are span-merges of the same four-column grid, so QuickTiler has no notion of a “current layout” to switch between. It has one flat list of zones and three cycles.

Key Cycles through
Tile left left quarter → left half
Tile right right quarter → right half
Tile center center half → center top third → center bottom two thirds

The center thirds exist for the common arrangement of a video call above a terminal.

Which zone a window is in is read back from its own geometry on every keypress. Nothing is remembered, so cycling works on windows that some other tool placed, and there is no state to go stale. The gap between windows is applied by insetting the work area and splitting each internal boundary, so neighbors end up exactly one gap apart and two zones sharing a fraction resolve to the identical pixel — no seam, and no lost pixel on an odd gap.

Shortcuts

Every default was checked against the shortcuts GNOME binds out of the box, so none of them collide and you do not have to unbind anything.

Action Default
Tile left Super+Ctrl+←
Tile right Super+Ctrl+→
Tile center Super+Ctrl+↑
Maximize Super+Ctrl+↓
Focus left Super+[
Focus right Super+]
Swap left Super+Ctrl+[
Swap right Super+Ctrl+]
Move to next monitor Super+Ctrl+M
Move to previous monitor Super+Ctrl+Shift+M

The split is deliberate: Super+Ctrl moves windows, and bare Super+bracket moves focus without touching anything.

Focus and swap both cross monitors. Frame rectangles are absolute, so the monitor to your right is simply where the windows further right are, and a swapped window lands exactly where its neighbor was.

Two windows sharing a horizontal center — the center top and bottom thirds, for instance — are not neighbors of each other. The comparison is strictly horizontal, and there is no vertical navigation yet.

Install

Needs GNOME 49 or newer. From the latest release, with no clone and no toolchain — gnome-extensions ships with GNOME Shell itself: 

curl -LO 'https://github.com/Ghost-Assembly/quicktiler/releases/latest/download/quicktiler@napalm255.github.io.shell-extension.zip'
gnome-extensions install --force 'quicktiler@napalm255.github.io.shell-extension.zip'

That unpacks the extension and compiles its settings schema, so there is no separate glib-compile-schemas step. Log out and back in — Wayland cannot reload the Shell in place — then turn it on: 

gnome-extensions enable quicktiler@napalm255.github.io

From a clone:

just setup
just install
just enable

Log out and back in if the Shell does not pick it up. just prefs opens the preferences window, just logs follows the extension’s output, and just disable turns it off again without uninstalling.

Upgrading from Tiler 0.1.0

QuickTiler was called Tiler up to 0.1.0, and the rename changed the extension’s uuid. GNOME identifies an extension by that uuid, so 0.2.0 installs alongside the old one rather than replacing it, and both try to claim the same shortcuts — only one of them can. Remove the old one first: 

gnome-extensions uninstall tiler@napalm255.github.io

The gap and shortcut settings do not carry over; they live under the old schema path and are set again in the preferences window.

Quick settings

The tile sits in the system menu, under the same panel as the volume and network controls. It is a QuickSettings.SystemIndicator holding one QuickMenuToggle, added through addExternalIndicator() so the Shell places it relative to brightness and background apps. There is deliberately no permanent top bar icon: one that never changes is noise, and this extension has no status to report between keypresses.

Clicking the tile pauses the keyboard shortcuts. Every accelerator is released, so it goes back to whatever else claims it, and clicking again takes them back. The menu header says which state it is in.

Clicking the arrow opens the menu: the four groups of actions — tile, focus, swap and monitor — each row showing the shortcut it currently holds and acting on the focused window when clicked. The tile teaches the keyboard rather than replacing it. Rows keep working while the shortcuts are paused, because the pause is about the keyboard only.

Why a row does not read the focused window. Opening the menu takes a Clutter grab, and Mutter's focus window can be null for as long as it is held. A row that read the display at click time could act on nothing at all, with nothing logged to say so, so modules/panel.js tracks the last window it saw focused and passes it to QuickTiler.run(). The window still goes through the same policy checks as a focused one, so a window that has since closed is rejected exactly as one that was never eligible.

Preferences

The preferences window has four things in it: whether the quick settings tile is shown, whether the keyboard shortcuts are registered at all, the gap between tiled windows and at the screen edge, and every shortcut itself.

The shortcuts switch is the same pause the tile writes. It is here as well as on the tile because it has to be: with the tile hidden there is no tile to click, and this is the only way back. Turning the tile off builds no actor at all, which is what lets the extension go back to costing nothing between keypresses.

Assigning a shortcut that another QuickTiler action already holds clears it from that action first. Leaving both set would not work: Mutter registers whichever it sees first and refuses the other, so one of the two would show as bound in the preferences window and quietly do nothing.

Architecture

The code is split so that every decision is testable off the Shell. Each module below imports nothing at all — not gi://, not resource:/// — so Vitest runs it directly on Node.

Module Owns
modules/zones.js The zone table, the projection to pixels, zone matching and cycling.
modules/windows.js Which windows may be placed and which may take focus. Worth isolating because getting one wrong is silent — the shortcut simply does nothing and no error is logged.
modules/neighbours.js Which window lies next to another in a given direction. Ties break on Mutter’s stable sequence, because list_windows() has no documented ordering.
modules/actions.js The single list of actions, shared with the preferences process. A test reads the gschema and fails if they drift.
modules/shortcuts.js The rules for assigning accelerators: what may be bound, what the capture dialog does about a keypress, and which action already holds a shortcut.
modules/accelerator.js How a shortcut is spelled for a reader — <Super><Control>Left becomes Super+Ctrl+←. The Shell has no Gtk, so Gtk.accelerator_get_label is unavailable to the menu and the text is worked out here. The same module is what the tests compare this site against.
modules/settings.js The names of the settings that are not keybindings, written once rather than as string literals in the three files that read and write them.

modules/quicktiler.js is the only file that touches Meta or Shell, modules/panel.js the only one that touches St, Clutter, PopupMenu or QuickSettings, and prefs.js the only one that touches Adw and Gtk. All three read facts off the toolkit and act on them; the decisions belong to the modules above.

Testing

modules/quicktiler.js and modules/panel.js are unit-tested all the same. vitest.config.js aliases the gi:// and resource:/// specifiers to stubs in tests/stubs, and tests/support models the parts of Mutter the extension actually depends on — notably that a maximized window reports the work area as its frame rect, and that allows_resize() is false while a window is maximized. Every bug fixed in that file has a regression test that fails without its fix.

scripts/headless-check.sh boots a throwaway Shell and checks that the extension enables, disables and re-enables without leaking a signal and without a JavaScript error. It presses no keys and asserts no geometry: it is a lifetime check against a real Shell, where the unit suite is what covers placement.

Why prefs.js has no coverage. Everything it used to decide now lives in modules/shortcuts.js. What is left is Adw and Gtk widget construction, which a unit test could only check against stubs of the toolkit — that tests the stubs, not the code.

The exclusion is written into both vitest.config.js and sonar-project.properties so the two cannot disagree.

Packaging

A GNOME Shell extension ships as a plain ZIP with a required layout. metadata.json must sit at the archive root, never inside a nested folder, and the file is conventionally named <uuid>.shell-extension.zip. The required metadata keys are uuid, name, description and shell-version; version is assigned by extensions.gnome.org when you upload, and version-name is an optional string shown to people.

GNOME ships an official packer, gnome-extensions pack, which knows that layout and can bundle a GSettings schema, translations and extra sources. QuickTiler does not use it to build, because gnome-extensions lives in the gnome-shell package and CI has no GNOME — depending on it would pull the whole desktop onto every runner. just build uses plain zip instead.

The official tool is kept as the authority anyway. just pack-check runs it and compares its output against the built zip, failing on any difference, so the hand-rolled archive cannot drift from what GNOME itself would produce. It needs a real Shell, so it runs locally as part of just test-live.

Every shipped icon is decoded, not just packed. An icon that fails to load is completely silent: gnome-shell draws nothing and logs nothing, so the first report is a person saying there is no icon. A long XML comment placed before the <svg> element is enough to do it — it defeats gdk-pixbuf's format sniffing — which is why the comment in icons/quicktiler-symbolic.svg sits inside the element. scripts/pack-check.sh loads each icon at 16×16 through scripts/icon-check.js and fails if it does not decode, or decodes to nothing visible. Neither the unit suite nor the headless check looks at an icon.

Releasing

Set version-name in metadata.json and version in package.json to the new version, commit, then tag and push: 

git tag -a v0.2.0 -m 'release v0.2.0'
git push origin v0.2.0

The tag drives everything. CI checks that it matches the version in both files and stops before building if it does not — a release titled v0.2.0 containing a zip that tells GNOME it is 0.1.0 is worse than no release. It then runs the full suite, builds the zip and attaches it to a GitHub release. Run just test-live before tagging, since neither the headless check nor the packer check runs in CI.

Uploading to extensions.gnome.org can be scripted — gnome-extensions upload takes --user, --password-file and --accept-tos: 

gnome-extensions upload --user YOU --password-file - \
    quicktiler@napalm255.github.io.shell-extension.zip

It is deliberately not wired into the release workflow. It authenticates with your extensions.gnome.org account password rather than a scoped token, and that does not belong in CI secrets. Every upload goes to human review regardless, so automating it buys little.

Development

just            # list every recipe
just fmt        # prettier and eslint --fix, in place
just test       # unit suite, runs on Node in about a fifth of a second
just coverage   # the same suite with a coverage report
just lint       # eslint, prettier, gschema and shellcheck
just security   # gitleaks, trivy, osv-scanner, actionlint, zizmor
just build      # the installable zip
just ci         # everything above — what CI runs
just test-live  # headless Shell smoke test, then the packer check
just docs       # serve this site locally
just run        # nested Shell for trying things by hand
just clean      # remove node_modules, coverage and build output

mise.toml pins every tool, so just ci behaves the same locally and on a runner. gjs, glib-compile-schemas, gnome-shell and gnome-extensions come from the system rather than mise, because they have to match the Shell you are targeting.
